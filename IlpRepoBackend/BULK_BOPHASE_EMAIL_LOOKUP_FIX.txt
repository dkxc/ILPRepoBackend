## ?? Bug Description

**Problem**: When calling `POST /api/BoPhases/batch/11` with valid trainee data, 
the API was returning error: "Trainee with email aswin@gamil.com not found"

**Symptom**: The trainee exists in the database with that exact email, but the 
lookup was failing.

## Root Cause

The `UserRepository.GetByEmailAsync()` method was performing a **case-sensitive, 
exact string match** on emails without trimming whitespace:

```csharp
// BEFORE (case-sensitive, no trimming)
return await _context.Users.FirstOrDefaultAsync(u => u.Email == email);
```

This caused lookups to fail if:
1. Email had leading/trailing whitespace
2. Email case didn't match exactly (e.g., "Aswin@gamil.com" vs "aswin@gamil.com")
3. Any invisible characters were present

## The Fix

### Modified File
`IlpRepoBackend.Infrastructure\Repositories\UserRepository.cs`

### Changes Made

Updated all email-related methods to:
1. **Trim whitespace** from input
2. **Convert to lowercase** for case-insensitive comparison
3. **Handle null/empty strings** properly

#### 1. GetByEmailAsync
```csharp
// BEFORE
public async Task<User?> GetByEmailAsync(string email)
{
    if (string.IsNullOrEmpty(email))
        return null;

    return await _context.Users.FirstOrDefaultAsync(u => u.Email == email);
}

// AFTER ?
public async Task<User?> GetByEmailAsync(string email)
{
    if (string.IsNullOrWhiteSpace(email))
        return null;

    var normalizedEmail = email.Trim().ToLowerInvariant();
    return await _context.Users
        .FirstOrDefaultAsync(u => u.Email.ToLower() == normalizedEmail);
}
```

## Why This Happened

### Common Sources of Email Variations

1. **User Copy/Paste**: Users might copy emails with extra spaces
2. **Excel/CSV Import**: Spreadsheets can add trailing spaces
3. **Form Input**: Web forms might not trim input properly
4. **Case Inconsistency**: Users type emails with different casing
5. **Database Entry**: Manual database entries might have formatting issues

### Real-World Example

User's data in Excel:
```
| Name  | Email                |  ? Extra space after email
| aswin | aswin@gamil.com      |
```

When this is uploaded, the email becomes `"aswin@gamil.com "` (with trailing space), 
causing the exact string match to fail.

## Best Practices Applied

### 1. Email Normalization
Always normalize emails before comparison:
```csharp
var normalizedEmail = email.Trim().ToLowerInvariant();
```

### 2. Case-Insensitive Comparison
Emails are case-insensitive per RFC 5321:
```csharp
u.Email.ToLower() == normalizedEmail
```

### 3. Whitespace Handling
Always trim input to handle user errors:
```csharp
if (string.IsNullOrWhiteSpace(email))
    return null;
```

### 4. Consistent Validation
Use `IsNullOrWhiteSpace` instead of `IsNullOrEmpty`:
```csharp
// ? Better - catches spaces
if (string.IsNullOrWhiteSpace(email))

// ? Misses whitespace-only strings
if (string.IsNullOrEmpty(email))
```

## Database Considerations

### Should We Normalize Emails in Database?

**Option 1: Normalize on Insert/Update (Recommended)**
```csharp
// In CreateTraineeHandler
user.Email = request.Email.Trim().ToLowerInvariant();
```

**Pros**:
- Consistent data in database
- Faster lookups (no ToLower() needed)
- Prevents duplicates with different casing

**Cons**:
- Need to update all create/update handlers
- Need migration to normalize existing data

**Option 2: Normalize on Query (Current Approach)**
```csharp
// In UserRepository
u.Email.ToLower() == normalizedEmail
```

**Pros**:
- No need to change existing handlers
- Works with existing data
- Easy to implement

**Cons**:
- Slightly slower queries (ToLower() called each time)
- Can still have duplicates with different casing in DB
